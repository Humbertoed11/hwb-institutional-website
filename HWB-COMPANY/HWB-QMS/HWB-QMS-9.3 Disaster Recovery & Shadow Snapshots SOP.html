Standard Operating Procedure: Disaster Recovery & Shadow Snapshots

1.0 Purpose

This document explains how to keep our systems running and protect our business data if files are broken, deleted by mistake, or if a server crash occurs. It provides a simple step-by-step path to backup our code, snapshot the PostgreSQL database, and restore everything instantly using physical snapshots and one-click restoration scripts.

2.0 Scope

This protocol applies to all active website pages, application settings, database structures, background workers, and artificial intelligence configurations inside our development and production workspaces.

3.0 Operational Roles

  • George (Systems Architect): In charge of starting emergency rollbacks and confirming that the system is fully healthy.
  • Peter (Recovery Specialist): In charge of creating regular backups, managing physical snapshot archives, and verifying restore procedures.
  • CEO (Humberto Dominguez): Final approval authority for any full system rollbacks.

4.0 Safety Snapshot Setup

To prevent loss of work, our system is protected by Peter's Recovery Directives. This creates full physical archives of the application code, environment configurations, and database binary dumps before any major architectural upgrade.

Important Safety Standard

Every time we begin a complex upgrade, we must create a physical snapshot archive and git checkpoint branch. This ensures we can easily undo our changes if an upgrade causes unexpected downtime.

5.0 Step-by-Step Procedures

5.1 Creating a Rollback Point (By Hand)

Before modifying any code, create a local safety snapshot:

  1. Open the terminal in the main project folder.
  2. Run the safety backup script: 
    .venv_agent/bin/python scripts/peter_sentinel.py
  3. The snapshot will be saved in the safety vault directory: 
    HWB-COMPANY/HWB-IT/HWB-IT-SYSTEM-LOGS/shadow_snapshots/[TIMESTAMP]/

5.2 The Panic Button: Restoring Broken Files

If files become corrupted during normal development, execute this quick restore:

  1. Navigate to the safety vault directory to locate your target backup timestamp folder: 
    HWB-COMPANY/HWB-IT/HWB-IT-SYSTEM-LOGS/shadow_snapshots/
  2. Copy all backed-up files from the chosen timestamp folder directly back into your active website directory: 
    cp -r HWB-COMPANY/HWB-IT/HWB-IT-SYSTEM-LOGS/shadow_snapshots/[TIMESTAMP]/* HWB-COMPANY/HWB-IT/HWB-IT-WEBSITE/

5.3 Live Database Spam Purging Procedure

When database queues are contaminated with spam entries, execute these steps to clean the records safely:

  1. Establish SCM connectivity to the Azure private network environment.
  2. Execute a transaction-level rollback purge of the target records: 
    BEGIN;
DELETE FROM "Leads" WHERE email LIKE '%@wshu.net';
DELETE FROM "PendingOutbox" WHERE email LIKE '%@wshu.net';
COMMIT;
  3. Verify that row counts match expectations and that outbox queues are clean.

5.4 Full Enterprise Snapshot & One-Click Rollback Script

Prior to major architectural overhauls (such as ARCH-001 and ARCH-002), a complete system snapshot is taken and stored in backups/:

  • Archive Location: backups/snapshot_2026-09-18_pre_enterprise_upgrade/ (464 MB total).
  • Binary Database Dump: hwb_dev_db_binary.dump (31 MB) — provides zero-loss table and sequence restoration.
  • Plaintext SQL Dump: hwb_dev_db_plain.sql (130 MB) — allows manual query inspection.
  • Complete Code Archive: hwb_it_website_code.tar.gz (305 MB) — tarball containing the entire website root.
  • Environment Archive: environment.env, docker-compose.yml, and requirements.txt.
  • Git Checkpoint: Ghost branch ghost-checkpoint-2026-09-18-pre-enterprise and tag checkpoint-pre-enterprise-upgrade-20260918.
  • One-Click Rollback Execution: To completely revert the system in under 60 seconds, run: 
    bash backups/snapshot_2026-09-18_pre_enterprise_upgrade/restore.sh
