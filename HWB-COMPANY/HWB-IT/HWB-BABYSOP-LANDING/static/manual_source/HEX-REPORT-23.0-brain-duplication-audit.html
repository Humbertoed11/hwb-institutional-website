Institutional Report: Cross-Lobe Duplication & High-Inference Audit

This report documents the results of an audit across the eleven neural lobes and supporting database schemas of HEXGROWTH. It identifies duplicate database tables, redundant document indexing, and conflicts in scoring scripts that must be fixed to ensure high-inference reasoning and data accuracy.

ℹ️ AUDIT FOCUS

To keep our land decisions accurate, we must ensure each brain lobe has a single, clear job. Having duplicate tables or conflicting data scripts leads to mixed results and wasted server storage.

1.0 Identified System Duplications

The system audit revealed three major areas of duplicate data storage and logic conflicts:

1.1 Database State Duplication: SystemCore vs. SystemState

The system maintains two separate tables to store session states and active variables: HEX_SystemCore and HEX_SystemState. When the sync script runs, it writes the exact same recovery data into both tables. This means we are storing the same parameters twice on every session reload.

  • Affected Script: hex_sync.py (writes to both tables).
  • Risk: Having two tables for state data increases the risk of data drift if one table is updated and the other is not.

1.2 Document Index Duplication: ManualIndex vs. KB_Library

The system stores QMS manuals twice in the database. The HEX_ManualIndex table is populated using the master index file to show manuals on the HUD. The HEX_KB_Library table is populated by a separate script that scans folders and generates word vectors for search.

  • Affected Scripts: hex_sync.py (populates ManualIndex) and HEX-PERSISTENCE-PROTOCOL.py (populates KB_Library).
  • Risk: Both tables store the same HTML manual contents, leading to wasted space and potential mismatches when manuals are updated.

1.3 Scoring Script Conflict: Real-World vs. Procedural TxDOT Miners

There are two scripts that calculate infrastructure scores for Lobe 2 (TxDOT Brain): HEX-MINER-TXDOT.py and HEX-MINER-TXDOT-PROCEDURAL.py. Both scripts write their scores to the same table (HEX_Lobe_Infrastructure) and overwrite each other's data on conflict.

  • Affected Scripts: HEX-MINER-TXDOT.py (real API data) and HEX-MINER-TXDOT-PROCEDURAL.py (procedural distance-based scores).
  • Risk: If both scripts run, they fight over the scores in the database, causing unstable ratings on the HUD.

2.0 High-Inference Consolidation Plan

To fix these issues and prepare the system for advanced cross-lobe reasoning, the following consolidation steps are proposed:

2.1 Consolidating Database State

The system will retire the legacy HEX_SystemCore table. All session load and save routines will be updated to target the new Tier 6 HEX_SystemState table exclusively. This establishes a single source of truth for all session variables.

2.2 Unifying the Knowledge Index

The system will merge the HEX_ManualIndex and HEX_KB_Library tables. We will add the mock/vector embedding columns to the index table, or configure the HUD endpoints to query HEX_KB_Library directly. The file-scanner script will become the primary way to sync and update all manuals in the system.

2.3 Establishing Lobe 11 (Scout Brain) as Ingestion Gatekeeper

To prevent duplicate API calls and scoring fights, all external scraping routines will be moved under Lobe 11 (Scout Brain). Lobe 2 (TxDOT) will no longer query external services directly. Instead:

  1. Lobe 11 dispatches a worker to collect real-world traffic data and writes it to a staging table.
  2. Lobe 2 reads from the staging table to calculate scores.
  3. If testing requires procedural values, a setting in HEX_SystemState will decide whether to use real API results or distance-based mock scores, rather than running conflicting scripts.
