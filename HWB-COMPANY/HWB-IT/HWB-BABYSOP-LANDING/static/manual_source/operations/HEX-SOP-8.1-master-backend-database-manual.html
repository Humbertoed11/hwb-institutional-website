Master Operating Procedure: Backend Database & Memory Architecture

Scope: Establishes global parameters, naming policies, container setups, security timing gates, and background synchronization engines for the HEXGROWTH Monolithic SQL Brain (Layers 0, 1, and 2).

1.0 Database Naming & Casing Standards

To ensure total query safety and code readability, all backend database objects must follow these rules:

  • Table Prefix: All tables must explicitly start with the prefix HEX_ (e.g., HEX_KB_Library). No exceptions are allowed.
  • Casing: Use PascalCase for table names and snake_case for column identifiers (e.g., last_updated).
  • Keys & Links: Primary keys default to id SERIAL. Foreign keys must link using explicit cascading deletes (ON DELETE CASCADE) to prevent orphan references.
  • Data Integrity: No synthetic or placeholder data is allowed. All scores, records, and geometry fields must originate from verified spatial, legal, or transactional endpoints.

2.0 Isolated Container Architecture (Attached Backing Services)

Adhering to Twelve-Factor app principles, the SQL database is isolated into its own virtual host space:

  • Backing Service Container: hex_postgis_db (running PostgreSQL 13 and PostGIS 3.1).
  • Persistent Volume: hex_data (protects transactional databases from container restarts).
  • Isolated Bridge Network: The database exposes no public ports to the host system. It communicates only with the web container (hex_web_app) inside a private virtual bridge (hex-net) using the link: postgresql://hexadmin:hexpassword@hex_postgis_db:5432/hex_dev_db.

3.0 The 3-Core Memory System & 7-Lobe Neural Map

3.1 Core Database Layers

The backend structures memory and system states across three primary SQL tables:

  1. Knowledge Library (HEX_KB_Library): Stores QMS manuals, SOPs, and compliance documents as plain text alongside their 1536-dimension SHA-256 semantic vector embeddings.
  2. Active State (HEX_SystemState): Tracks currently active project IDs, active lobes, map coordinates, and user configurations to maintain session state across reloads.
  3. Execution Registry (HEX_Telemetry): Low-level logs monitoring API query durations, miner schedules, and synchronizer execution results.

3.2 Operational Lobes & Scoring Range

Geospatial spatial layers are evaluated through seven domain brains that translate municipal, transport, utility, and environmental records into normalized scores (0.0 to 10.0):

  • City Brain (Lobe 1): Processes municipal code, permits, variance delays, and zoning boundaries.
  • TxDOT Brain (Lobe 2): Analyzes highway traffic counts, capacities, and egress bottlenecks.
  • Power Brain (Lobe 3): Monitors utility grid substations, capacities, and lag times.
  • Legal/Env Brain (Lobe 4): Tracks ALTA land ownership chains, easement records, and soil geotech checks.
  • Ranger Brain (Lobe 5): Integrates field verification audits and physical security variables.
  • Pulse Brain (Lobe 6): Crawls social feeds and news ticker sentiment logs to assess community friction.
  • Finance Brain™ (Lobe 7): Computes time-cost of capital, baseline cap rates, and pro-forma ROI values.

4.0 Synchronization Engine & Backing Services

4.1 Ingestion Engine (hex_sync.py)

On startup and index triggers, the synchronization engine maps HTML directories, updates relative URLs, and copies session metadata. It parses the flat files from HEX-QMS/ and writes them dynamically to the HEX_ManualIndex table, allowing the Flask web app to serve QMS documentation from SQL tables instead of executing slow file-system lookups.

4.2 Persistence Protocol (HEX-PERSISTENCE-PROTOCOL.py)

A background worker that scans document folders, hashes the text contents to generate deterministic mock embeddings, and registers the files inside the HEX_KB_Library semantic vector database.

4.3 Exception Capture & Ticker Sync

  • Uncaught Exception Middleware: Traps uncaught server errors and tracebacks, writing them as pending records into the HEX_KnowledgeScars database table to prevent bug regression.
  • Chat Console Ingestion (HEX-SYNC-TRANSCRIPT.py): Periodically parses terminal activity transcripts and commits them to the HEX_InteractionCore table.

5.0 Session Security & Timeout Rules (Hybrid Model)

To satisfy corporate data security policies, user sessions are automatically timed out after 15 minutes (900 seconds) of inactivity using a two-layer security watch:

  1. Server-Side Flask Enforcer: Sets PERMANENT_SESSION_LIFETIME = timedelta(minutes=15) with cookie lifetime updates (session.permanent = True) processed on each valid request intercept.
  2. Client-Side JS watchdog: Monitors mouse and key interaction events on the client canvas, executing an immediate redirection to the /logout endpoint if no user input occurs for 900 seconds.
