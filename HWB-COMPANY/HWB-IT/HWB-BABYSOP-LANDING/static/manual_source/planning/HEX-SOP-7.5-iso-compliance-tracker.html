STANDARD OPERATING PROCEDURE: ISO 9001 Compliance Tracker & Document Control Standard

Purpose: Establishes the operational framework to satisfy ISO 9001:2015 requirements for a formal certification audit within 12 months. This SOP defines document control, internal audits, corrective actions, and management reviews.

1.0 Documented Information Control (ISO Clause 7.5)

To ensure consistency and tracebility, all project files must comply with these guidelines:

  • Unique Identification: Every QMS document must possess a unique ID (e.g., HEX-SOP-X.X or HEX-REPORT-X.X).
  • Version Control: Updates require incrementing the version number (e.g., from 1.0.0 to 1.1.0) and logging changes in the revision section.
  • Standard Template: Documents must use the uniform snippet format (wrapped inside a sop-card container with a sop-meta header card). Standalone HTML wrappers are prohibited.
  • Authoritative Record: The PostgreSQL database table HEX_ManualIndex serves as the active system of record, synchronized from offline disk templates via scripts/hex_sync.py.

2.0 Risk Planning & Objectives (ISO Clauses 6.1 & 6.2)

2.1 Risk Registry & Mitigation

System bugs and operational risks must be logged immediately in docs/PROBLEMS-TO-SOLVE.md. The log tracks:

  • Friction Identification: Specific description of the defect or issue.
  • Impact Level: Rated as Low, Medium, High, or Critical.
  • Lobe Category: The specific software system affected.
  • Resolution Status: Must be marked as PENDING, ACTIVE, or RESOLVED.

3.0 Internal Audits & Performance Evaluation (ISO Clause 9.2)

The Systems Architect (George Bytes) will perform regular internal audits to maintain audit readiness:

  • Audit Frequency: Internal audits will be performed semi-annually (every 6 months).
  • Audit Methodology: DMAIC Six Sigma questionnaires will be used to audit backend scaling, map rendering, and API security. Results must be compiled in the Six Sigma Black Belt Project Ledger.

4.0 Corrective Actions & Nonconformities (ISO Clause 10.2)

When a system nonconformity is discovered, the following corrective action process must be triggered:

  1. Log: Identify the issue and register it in docs/PROBLEMS-TO-SOLVE.md.
  2. Contain: Deploy temporary blocks or security patches.
  3. Analyze: Conduct a root cause analysis using 5-Whys or FMEA techniques.
  4. Implement: Update code and local templates, then execute scripts/hex_sync.py to sync changes to PostgreSQL.
  5. Verify: Assert correct page rendering and API execution using automated command-line tests.
