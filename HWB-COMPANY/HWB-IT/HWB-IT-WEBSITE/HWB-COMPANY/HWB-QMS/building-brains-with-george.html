Chapter 2: Case Study #1 — The Missing Edit Button Handler & Modal Crash

1. The Human Vibe Directive: Humberto clicked the Edit button under User Management and said: "Check the edit button under actions. I click on it and does not open up the next form."

2. The Communication Gap & Mistake: When we first created the User Management screen, I assumed the standard openModal() JavaScript helper was inherited globally. In reality, openModal() was defined inside a specific template (backoffice_operations.html), not in the base template. Calling it threw an invisible Uncaught ReferenceError in the browser console. Additionally, passing string arguments directly inside inline onclick attributes broke whenever a user's name contained single quotes.

3. George's Response & Analysis: Instead of asking Humberto to check browser developer tools, I immediately audited the template inheritance hierarchy, located the missing function, and re-architected the event binding.

4. The Production Solution:

  • Moved openModal(id) and closeModal(id) to backoffice_base.html so every page has access to modal controls.
  • Bound user account data cleanly using HTML data- attributes (data-id, data-fullname, data-role, data-status, data-perms).
  • Created openEditUserModalFromRow(this), which reads row attributes cleanly with zero risk of JavaScript syntax errors.

💡 Pro-Tip for AI Builders: Never pass complex string parameters inside inline HTML event attributes (like onclick="func('name')"). Always use HTML5 data- attributes and pass this. It makes your code 100% immune to quote-escaping bugs!

Chapter 3: Case Study #2 — The 200-Row Scrolling Trap & In-Modal Governance

1. The Human Vibe Directive: Humberto reviewed our first layout for role permissions and asked a sharp question: "If we have 200 users in the system, the system module showing all access options will be displayed at the end of the 200 user list away from the user's eyes?"

2. The Communication Gap & Mistake: I had initially placed the Role Access Rights Matrix at the bottom of the User Management page. While technically functional, it created terrible user experience (UX) friction: an admin would have to scroll past 200 user rows just to change a role permission!

3. George's Response & Analysis: Humberto proposed moving the permissions panel directly inside the Edit User Account Modal (Option 1). I evaluated Option 1 vs. Option 2 (Sub-Tabs) and confirmed that Option 1 was 100% user-centric, zero-scrolling, and allowed per-user permission overrides.

4. The Production Solution:

  • Removed the standalone bottom matrix table completely.
  • Embedded an interactive Module Access Rights Panel directly inside the #modal-edit-user form overlay.
  • Added dynamic JavaScript (updateModalPermsFromRole) so selecting a role (*Sales*, *Manager*, etc.) automatically checks default permissions, while still letting admins customize individual module access per user.
  • Added a JSON column custom_permissions to the "Users" database table to store per-user overrides atomically.

💡 Pro-Tip for AI Builders: When your AI suggests placing a feature on a page, ask yourself: "Where will the user's eyes be when they need this?" If a feature requires scrolling past dozens of rows, ask your AI to integrate it into a modal overlay or a tab rack.

Chapter 4: Case Study #3 — Self-Deletion Protection (Poka-Yoke Safeguard)

1. The Human Vibe Directive: Humberto noticed that Mirna Rondinella's user account row showed an Edit button but no Delete icon, and asked: "The user Mirna Rondinella... under actions I see the edit button but it is missing the delete icon. Why?"

2. The Perception Gap: Mirna was the currently logged-in active user account. If a delete button were displayed for the active user, a single accidental click could cause self-deletion, locking the administrator out of the system mid-session.

3. George's Response & Explanation: I explained the Poka-Yoke Safeguard logic clearly: 

{% if current_user.id != user.id %}
    <!-- Render delete button for other user accounts only -->
    <button type="submit">Delete</button>
{% endif %}

4. The Production Solution: Maintained the self-deletion safeguard while keeping the Delete button active for all non-logged-in team accounts.

💡 Pro-Tip for AI Builders: Always instruct your AI to build "Poka-Yoke" (mistake-proofing) safeguards into administrative actions. Never allow an active user to delete their own account or drop active session tables without explicit multi-step confirmation.

Chapter 5: George's Guide to Better AI Communication

4 Gold Rules for Vibe-Coding Success
  1. Give Me the "Why", Not Just the "What": Explaining the business context (e.g., *"Clients want to edit permissions per user, not per role"*) allows your AI to design the exact right solution on the first try.
  2. Use "Plan Mode" Before Writing Code: Ask your AI to show CLI ASCII mockups and multi-choice options first. Aligning on design saves hours of rewrites.
  3. Short Confirmations Accelerate Speed: Concise prompts like "approved option 1" or "show CLI mockup" preserve token context and keep execution fast.
  4. Log Friction Immediately: Never let bugs sit. Have your AI log every error immediately to a tracking file (like PROBLEMS-TO-SOLVE.md) for permanent corrective audits.
