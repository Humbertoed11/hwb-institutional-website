Standard Operating Procedure: Spam Protection & Communication Integrations

1.0 Purpose

This Standard Operating Procedure (SOP) defines the operational guidelines for protecting the HWB marketing lead ingestion pipeline from automated bot spam. It also codifies the deployment of the Telegram and Telegra.ph communication bridge to deliver real-time systems reports and walkthroughs directly to executive mobile devices.

2.0 Scope

This procedure applies to the live website ingestion route (/get-quote) in the main web application, the live PostgreSQL database queues (Leads and PendingOutbox tables), and all automated administrative scripts executed within the HWB-SIGMAJAN cloud infrastructure.

3.0 Procedure

3.1 Live Database Spam Auditing and Clean-up

When the systems administrator identifies a spam campaign in the pipeline (e.g., matching a domain like @wshu.net or containing fraudulent money-transfer URLs):

  • Secure Azure Management tokens using Service Principal credentials.
  • Connect to the private-network PostgreSQL database using Kudu's VFS PUT endpoint to upload a secure database runner.
  • Execute a database transaction (BEGIN ... COMMIT) to purge both the fraudulent lead rows and the pending notification emails to protect the outbox queue from distributing spam.

3.2 Honeypot Ingestion (Spam Blackhole Pattern)

To eliminate bot spam without triggering retry loops:

  • Intercept form submissions in the get_quote() controller before database writes or email alerts occur.
  • Inspect the company and name inputs for spam signatures:
    • Link Signatures: Presence of http://, https://, graph.org, .org/, .net/, or .com/.
    • Semantic Signatures: Presence of typical transaction spam phrases (e.g., us dollars, usdc, transfer of, payment, get the transfer, balance).
  • The Silent Blackhole: If spam is detected, immediately skip all database inserts and outbox email writes. Return a simulated successful completion page (quote_success.html) to the bot so it stops attempting to submit.

3.3 Telegraph & Telegram Communication Bridge

To establish secure, readable, and highly mobile executive updates:

  • Telegra.ph Publishing: Use the anonymous Telegraph API to dynamically register account tokens and compile local HTML walkthroughs into structural JSON node formats. Publish these pages to the public web for instant mobile-optimized readability.
  • Telegram Notifications: Configure TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID within the local .env file. George will automatically dispatch the newly generated article link directly to the CEO's Telegram app using the sendMessage API.
Note

Always keep private Telegram credentials and Telegraph account access tokens stored exclusively in the git-ignored .env configurations on the host systems.

4.0 Verification (Zero-Defect Check)

  • Honeypot Validation: Submit a mock lead containing a link in the company name. Confirm that the page returns success but the database row count remains unchanged.
  • Telegraph Validation: Execute python3 scripts/test_telegraph.py. Confirm that it generates a clean HTTP 200 response and outputs a functional telegra.ph URL.
  • Fidelity Compliance: Ensure all modified code compiles correctly without errors using python3 -m py_compile prior to production deployment.
