Standard Operating Procedure: Backend Architecture, RBAC Gateway & PII Cryptography

1.0 Purpose

This procedure establishes the Zero-Hotfix Enterprise Mandate, the 5-Pillar Enterprise Deduplication & Smart Merge Engine, the 5-Pillar Enterprise Marketing Campaign Readiness Architecture, and cryptographic security standards across all software systems at HWB Cleaning Services LLC. The purpose is to eliminate quick patches, temporary workarounds, duplicate database records, and bounced emails. Every engineering change must be designed to enterprise standards, protecting company data and preventing defects from recurring.

2.0 Scope

This standard applies to all software engineers, autonomous AI agents, technical contractors, and administrative systems operating within the HWB ecosystem, including the web application, background workers, PostgreSQL 16.15 databases, and APIs.

3.0 The Zero-Hotfix Enterprise Mandate

The Institutional Law

From September 18, 2026 onward, only enterprise-level solutions are permitted in the HWB codebase. Ad-hoc hotfixes, local workaround scripts, and quick patches are strictly prohibited.

When an issue or security gap is discovered, developers must find the root cause in the architecture and fix the system as a whole, rather than patching a single screen or endpoint.

4.0 The 6 Pillars of Enterprise Architecture

Pillar Core Requirement Industrial Purpose
1. Root Cause Engineering Solve systemic causes, never mask symptoms with local if statements. Prevents identical bugs from emerging in adjacent modules.
2. Centralized Gateway Enforce access control at the request gatekeeper (@app.before_request). Fail-safe default: new endpoints are secure by default.
3. Declarative Contracts Use explicit decorators like @roles_required on endpoints. Code is readable, self-documenting, and impossible to bypass.
4. Defense-in-Depth Triple protection: Database checks + Backend interceptors + Clean UI rendering. Even if a user bypasses the UI, backend locks stop unauthorized requests.
5. Automated Testing Mandatory test scripts verifying both authorized and blocked paths. Proves code works before deployment with zero guesswork.
6. Immutable Audit Trail Log every access violation to GlobalActivities and SecurityAuditLogs in PostgreSQL. Provides full accountability and traceability for ISO audits.

5.0 Role-Based Access Control (RBAC) & Row-Level Sales Territory Quarantine Standard (BUG-125–BUG-130 & Migration 042)

User access is partitioned into distinct operational zones based on verified roles and row-level ownership:

  • Executive & Admin: Global system access, Warchest financial controls, user provisioning (including password eye-toggles and force_pwd_reset enforcement), and strategy modules.
  • Manager: Operations oversight, accounts, and SOP manual. Restricted from user provisioning and financial Warchest.
  • Operator: Daily cleaning dispatch, work orders, and commercial lead pipeline.
  • Sales (Strict Territory Isolation): Dynamic post-login routing directs Sales accounts to their authorized workspace while enforcing strict row-level territory isolation across four modules:
    • Commercial Leads (?view=leads) & Calling Workstation (/sales-desk): Enforces owner_id = current_user.id so representatives only see and call leads explicitly assigned to them. Calling scripts dynamically replace {Caller} with the representative's first name while persisting custom per-user scripts in user_scripts.
    • Active Clients (?view=accounts): Enforces assigned_rep_id = current_user.id so representatives only see client accounts assigned to their territory or promoted by them.
    • Commercial Construction Bidding (?view=construction_bids): Enforces assigned_rep_id = current_user.id (Option A, Migration 042) so representatives only view and manage construction bids assigned to their user ID via POST /api/v1/construction-bids/<bid_id>/assign-rep.
    All bulk data exports, payroll summaries, and sensitive workforce endpoints remain blocked with HTTP 403.

6.0 Sensitive PII Vault & Cryptographic Architecture (SEC-001)

All sensitive worker identifiers and financial credentials are protected by the SigmaFidelity™ Cryptographic Core (core/security.py):

  1. AES-256 Fernet Cipher: Social Security Numbers, ITINs, and direct deposit checking/savings accounts are encrypted at the column level before writing to PostgreSQL (ssn_encrypted, direct_deposit_account_encrypted).
  2. Deterministic Key Derivation: The cipher key is derived deterministically via SHA-256 hashing of system environment secrets (PII_ENCRYPTION_KEY / SECRET_KEY), guaranteeing persistence across container restarts without key drift.
  3. Zero Plaintext API Exposure: All general endpoints (GET /api/v1/hr/employees and GET /api/v1/hr/employees/<id>) strip encrypted ciphertext blobs and transmit only masked strings (***-**-#### and ••••••••####).
  4. Audited Timed Reveal Protocol: Authorized personnel requesting unmasked views must use POST /api/v1/hr/employees/<id>/reveal-ssn. The gateway checks credentials, records an immutable audit log to "GlobalActivities" (stamping user ID, username, and IP address), and returns the decrypted value with a strict 30-second client-side lifetime.
  5. Automatic Security Violation Logging: If unauthorized roles (e.g. Sales) attempt to call sensitive reveal endpoints, the gateway returns HTTP 403 Forbidden and writes an automatic SECURITY_VIOLATION event to the audit ledger.

7.0 The 5-Pillar Enterprise Deduplication & Smart Merge Engine (BUG-122 & Migration 041)

To prevent duplicate database rows when a subcontractor, job applicant, commercial quote prospect, W-2 employee, customer account, training student, or bid solicitation is submitted more than once across different weeks, all 6 intake and backoffice creation modules enforce a unified 5-Pillar architecture:

  1. Pillar 1 — Sanitizer & Identity Key Normalization (core/services/sanitizer.py): Inbound payloads are normalized via extract_phone_digits() (10-digit US core stripping country codes and punctuation), clean_email() (lowercase trimmed), normalize_business_name() (stripping corporate suffixes like LLC/Inc and collapsing whitespace), merge_comma_list() (case-insensitive union of specialties/tags), and clean_city() (stripping trailing state suffixes such as ", TX").
  2. Pillar 2 — Functional Database Indexes (Migration 041 in database/schema_engine.py): PostgreSQL 16.15 enforces functional indexes across "SubcontractorPartners" (idx_subcontractors_unique_phone_digits), "JobApplicants" (idx_jobapplicants_phone_digits), "Leads" (idx_leads_phone_digits), "Employees" (idx_employees_phone_digits), "Customers" (idx_customers_phone_digits), "ConstructionBids" (idx_construction_bids_gc_project), and "InstitutionalBids" (idx_institutional_bids_solicitation).
  3. Pillar 3 — Non-Destructive Smart Profile Merge: When an existing record is matched across any of the 6 modules—Subcontractors (/api/v1/workforce/subcontractor), Job Applicants (/api/v1/workforce/apply), Commercial Quote Leads (/get-quote & /admin/add-lead), HR Employees & Customer Accounts (/api/v1/hr/onboard, /api/v1/leads/<id>/promote, /admin/add-account), SigmaAcademy™ Enrollments (/api/v1/academy/assign), or Commercial/Institutional Bids (/api/v1/construction-bids/create & /api/v1/institutional-bids/create)—the backend preserves the master primary key and original registration timestamp, merges any new capabilities or updated numbers, and returns status: "already_registered".
  4. Pillar 4 — Automated Confirmation Receipts & Staff Alert Suppression (core/services/notification_service.py): First-time and returning registrants receive a branded Reference ID confirmation receipt (SUB-#00XX, APP-#00XX, LEAD-#00XXX) in their email inbox, while duplicate internal Telegram and Outlook staff alerts are suppressed on repeat updates.
  5. Pillar 5 — Privacy-Safe Frontend Status Cards: Public forms (templates/work_with_us.html and templates/quote_success.html) display a blue Already Registered — Profile Updated banner showing the registrant's Reference ID without leaking private database fields.

8.0 The 5-Pillar Enterprise Marketing Readiness & 4-Safeguard Daycare Miner Architecture (BUG-131 & Migration 043)

To guarantee zero hard bounces and complete sender reputation protection across all outbound commercial email campaigns, PostgreSQL 16.15 and the background ingestion daemons enforce a 5-Pillar readiness architecture:

  1. Pillar 1 — Self-Maintaining Database Trigger (trg_leads_campaign_readiness): Installed via Migration 043, fn_leads_compute_campaign_readiness() fires on every INSERT or UPDATE of email, phone, status, do_not_email, industry_sector, or email_mx_verified on "Leads". It automatically normalizes email addresses, formats 10-digit US phone numbers to (###)-###-####, classifies email_inbox_type (DIRECT_PERSONAL vs. ROLE_INBOX), and evaluates a 6-gate check to set campaign_ready (TRUE/FALSE) and email_hygiene_status.
  2. Pillar 2 — DNS Mail-Server (MX) Verification Table ("EmailDomainHealth"): Stores TCP/UDP DNS MX verification results across all 5,061 unique email domains (4,991 verified live domains; 70 expired/non-existent NXDOMAIN domains quarantined as DEAD_DOMAIN_NO_MX).
  3. Pillar 3 — Permanent Unsubscribe & Bounce Suppression Ledger ("EmailSuppressionList"): Synchronized with both /unsubscribe (blueprints/public.py) and the Microsoft Graph outbound gateway (core/services/email_service.py) so opted-out or hard-bounced addresses can never be re-emailed even if re-imported by an external scraper.
  4. Pillar 4 — Multi-Site Owner Deduplication & Smart Greeting Fallbacks (blueprints/crm_api.py): Campaign queue endpoints filter strictly by campaign_ready = TRUE and DISTINCT ON (LOWER(TRIM(email))) ordered by highest contract value so multi-location facility owners receive one email per campaign batch, with automatic greeting fallbacks ("Hi there" / "Facility Director").
  5. Pillar 5 — 4-Safeguard Daycare Registry Miner (scripts/daycare_registry_sync.py): Enforces paginated Socrata ingestion, COALESCE preservation of website-mined emails, a ≥ 7,500 active-record circuit breaker, explicit per-permit closure verification (operation_status = 'N'), active-deal protection, and self-healing reactivation with automatic cancellation of unsent "Outbox" drafts for closed facilities.

9.0 4-Stage 1099 & W-2 Encrypted Onboarding Vaults, Savepoint Isolation & 5-Layer Universal Input Masking / Transaction Receipt Architecture (BUG-138–BUG-142 & Migrations 046–050)

  1. Self-Healing IAM Password Recovery (BUG-138 & Migration 046): /forgot-password supports case-insensitive lookup across username, email, and full name (LOWER(full_name)), automatically heals missing reset columns on "Users", and writes immutable delivery records to "PasswordResetAuditLedger".
  2. AES-256 PostgreSQL BYTEA Document Vaults & Locked ReportLab PDF Certificates (BUG-139–BUG-140 & Migrations 047–048): Uploaded 1099 (W-9, COI) and W-2 (W-4, I-9, Photo ID, Voided Check) onboarding files are parsed by AI/PDF extractors (subcontractor_doc_extractor.py and employee_doc_extractor.py), encrypted via AES-256 Fernet cipher, and stored inside PostgreSQL "SubcontractorDocuments" and "EmployeeDocuments" (encrypted_payload BYTEA + SHA-256 hash) so container restarts never lose compliance files. Electronic signatures generate locked ReportLab PDF certificates (MSA, TX DWC-83, and ISO 9001 Clause 7.2 Job Descriptions).
  3. PostgreSQL Savepoint Transaction Isolation (BUG-141 & Migration 049): All helper queries inspecting optional configuration tables (such as _get_subcontractor_onboarding_mode(cur) querying "SystemSettings") MUST execute inside a dedicated SAVEPOINT sp_sys_settings block with ROLLBACK TO SAVEPOINT on exception so a missing table never aborts the outer PostgreSQL transaction (InFailedSqlTransaction).
  4. 5-Layer Universal Input Masking & Tamper-Evident Transaction Receipt Architecture (BUG-142 & Migration 050):
    • Global Input Masking Engine (/static/js/sigma_input_masks.js): Auto-injected via main_app.py @app.after_request across all HTML pages with a self-healing MutationObserver. Enforces live keystroke masks and strict maxlength ceilings across EIN (XX-XXXXXXX, maxlength="10"), SSN/ITIN (XXX-XX-XXXX, maxlength="11"), US Phone ((###)-###-####, maxlength="14"), ZIP (#####-####, maxlength="10"), 9-digit ABA Routing (maxlength="9"), and 2-letter State (maxlength="2") fields, including dynamic EIN/SSN mask switching when Federal Tax Classification changes on 1099 onboarding.
    • Server-Side Canonical Sanitizer (core/services/sanitizer.py): Enforces clean_ein_or_ssn(), clean_ssn(), and clean_routing_number() before database persistence or AES-256 encryption.
    • Tamper-Evident Transaction Receipt Cards (#onboarding-receipt-card & #w2-receipt-card): Submitting or revisiting a completed 1099 or W-2 onboarding portal collapses the input form and displays a tamper-evident Transaction Receipt Card with deterministic Receipt IDs (HWB-1099-000XX-YYYYMMDD / HWB-W2-000XX-YYYYMMDD), SHA-256 signature verification, downloadable PDF certificates, and a controlled "Re-Open Form" toggle.

10.0 Verification (Zero-Defect Check)

  • All admin routes must declare explicit role requirements using @roles_required.
  • The centralized gatekeeper (@app.before_request) must automatically intercept out-of-bounds requests.
  • Templates must receive permissions through nav_access context engine without scattered manual role checks.
  • All employee queries must sanitize output dictionaries, ensuring no raw ciphertexts or unmasked bank accounts exist in memory.
  • Automated test suites verifying RBAC quarantine, PII encryption, 6-module enterprise deduplication, 5-pillar campaign readiness, and 5-layer input masking / onboarding transaction receipts (scripts/test_web_performance_rack_14.py — 20/20 passing) must pass 100% prior to any container deployment.
